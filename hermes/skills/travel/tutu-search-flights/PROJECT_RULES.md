# tutu-search-flights — правила проекта

Корень дерева документов. Читается перед любой работой с кодом.

**Главный принцип: правило, которое нельзя проверить командой, — пожелание.**
Прочитать правило и следовать правилу — разные вещи, и рассчитывать здесь можно только
на второе. Поэтому у каждого раздела ниже есть команда, тест или спека, которая его
удерживает. Правило без такой опоры в этот документ не попадает.

Имена фиксированы и одинаковы везде — в коде, в документах, в командах:
скилл `tutu-search-flights`, пакет `tutu_search_flights`, единственная команда `search`.

---

## 1. Что мы строим

Скилл поиска авиабилетов. Внутри скилла — CLI-утилита.

- **Команду запускает агент**, а не человек. `SKILL.md` объясняет агенту, когда и как её вызывать.
- CLI подключается к **MCP-серверу Туту как клиент**, вызывает его инструменты, получает данные
  о рейсах.
- CLI приводит ответ к своим типам, применяет правила отбора и печатает результат: машинный JSON
  для агента и готовый текстовый блок для конечного пользователя.

CLI **не** является MCP-сервером и не ходит к сайтам авиакомпаний напрямую.
Единственный источник данных — MCP-сервер.

### Кто потребитель

Потребителей два, и путать их нельзя:

| Потребитель | Что получает | Через что |
|---|---|---|
| Агент | строгий JSON фиксированной формы | stdout, `--format json` (по умолчанию) |
| Человек | готовый блок текста в нужном формате | `--format text`, агент отдаёт его как есть |

**Агент не собирает текст для человека сам.** Форматирование — работа CLI. Если в `SKILL.md`
приходится писать «не собирай ответ вручную», проблема не в тексте инструкции, а в выводе CLI —
чини вывод.

**Агент не сочиняет данные о рейсах.** Цены, времена, номера рейсов и ссылки приходят только
из MCP; агент выбирает среди них по `id` и ничего не досчитывает. Это не стиль, а защита от
галлюцинаций поверх настоящих данных.

## 2. Область MVP (версия 0.1)

**Входит:**

- один скилл, одна команда: `search`;
- один MCP-сервер, один-два его инструмента;
- маршруты: в одну сторону и туда-обратно, эконом;
- фильтры: дата, прямые/с пересадками, максимум пересадок;
- два формата вывода: `json` и `text`;
- `SKILL.md` по стандарту раздела 11;
- полный набор ворот качества из раздела 13 — с первого коммита, а не «потом».

**Не входит и не обсуждается до 0.2:** кэш на диске, несколько провайдеров одновременно,
бронирование, календари, парсинг сайтов, мультигород, сложные тарифные правила, вторая команда,
плагины.

Правило MVP: **узкая функциональность, полная инженерная основа.** Если выбор стоит между
«ещё одна фича» и «ворота качества» — выигрывают ворота.

### Три вещи, которые не режутся

Область можно сужать, но эти три пункта остаются в любой урезанной версии. Каждый из них —
измеренный факт из `docs/mcp-notes.md`, а не осторожность.

**Честная база цены.** Авиа отдаёт цену на всю группу (`basis: party_total`). Утилита, которая
молча умножит её на пассажиров или сравнит с ценой за место, соврёт в главном числе.

**Честная зона времени.** Один перелёт пересекает до трёх поясов и границу суток. Дата прилёта,
посчитанная в поясе вылета, — неверная дата.

**Честный отказ.** «Не смогли получить данные» и «рейсов нет» — разные ответы. Форма отказа
типизирована и различима агентом.

Область можно сужать по правилам раздела 2 — эти три пункта остаются в любой урезанной версии.

## 3. Как ведётся работа

**План → Подтверждение → Выполнение → Проверка.**

- Не пиши код, пока не прочитал существующий код в затронутой области.
- План — список конкретных файлов и изменений. «Улучшить архитектуру» планом не является.
- Изменение, затрагивающее публичный контракт, — сначала план, потом код.
- **Никогда не заявляй «исправлено», «работает», «тесты проходят» без запуска команды и её вывода.**
  Утверждение без вывода команды считается ошибкой.
- Каждое изменение заканчивается ответом на вопрос: *какой командой это проверено и что она вывела.*

### Порядок внутри шага

Спека краснеет → юнит-тесты краснеют → код → юнит-тесты зеленеют → спека зеленеет → `make check`.

Именно в этом порядке. Зелёная спека поверх красных юнитов означает, что юниты недотестированы.
Зелёная спека, написанная после кода, проверяет не поведение, а то, что код делает то, что делает.

### Размер шага

Работа приносится **минимальными проверяемыми кусками**, а не готовыми фичами.

- Один шаг = одно понятное изменение + спека на него + всё, что нужно, чтобы проверить его за
  один подход. Ориентир: дифф читается за один заход, порядка 200 строк.
- Найти следующий маленький независимый шаг — дороже, чем его реализовать. Это нормально:
  большая часть работы уходит на нарезку, и это дешевле, чем разбирать готовую большую фичу.
- Шаг, который нельзя проверить одной командой, нарезан неправильно — он не «сложный».
- **Непроверенные ветки не копятся.** Кусок либо принят сегодня, либо выброшен: завтра проект
  уйдёт вперёд, контекст выветрится, и переписать станет дешевле, чем разобрать.
- Готовая, но не принятая фича — это не задел, это будущий мусор.

### Форма отчёта

Каждый пакет закрывается отчётом одной формы — чтобы проверка не требовала расследования:

```markdown
## Пакет N: <что сделано>

### Ход
1. Спека `specs/<имя>.py`, сценарий «<имя>» — красный, причина: <какая>
2. Юнит-тесты `tests/<модуль>_test.py` — красные
3. Реализация `src/tutu_search_flights/<слой>/<модуль>.py`
4. `make specs` — N прошло; `make check` — вывод ниже

### Изменённые файлы
- `src/...` — что и зачем
- `specs/...`, `tests/...`
- `docs/...` — что задокументировано

### Вывод make check
<дословно>
```

## 4. Порядок выбора решения

Сверху вниз; следующий уровень — только если предыдущий не подходит:

1. **Не создавать** — нужна ли эта сущность вообще.
2. **Переиспользовать** существующий код проекта.
3. **stdlib**.
4. **Уже объявленная зависимость**.
5. Новая зависимость — только с явным обоснованием, записью в `pyproject.toml` и записью
   в `docs/decisions.md`.

### Свой минимум вместо чужого комбайна

Если из библиотеки нужны 5% функциональности — эти 5% пишутся прямо в проекте.

- Свои 50 строк под контролем лучше внешнего комбайна с чужими нюансами, лишними фичами
  и чужими уязвимостями. Понадобится поправить — правим.
- Правило действует только вместе со спеками: свой код без спеки — не упрощение, а долг.
- Запрещено без явной просьбы: новые слои, фабрики, реестры, `Protocol`, адаптеры,
  обёртки «на будущее».
- Рефакторинг обязан **уменьшать** число модулей и строк. Стало больше — это не рефакторинг,
  откатывай.

## 5. Архитектура

### Раскладка скилла

```
tutu-search-flights/
  SKILL.md              инструкция агенту: когда вызывать, как читать ответ
  AGENTS.md             навигатор по дереву документов, одна страница
  PROJECT_RULES.md      этот документ
  Makefile              единственный список команд проекта
  references/           подробности для агента, читаются по необходимости
  src/tutu_search_flights/
    core/               домен: типы, время, цена, события, правила отбора, ранжирование, рендер
    mcp/                единственное место, знающее про MCP: транспорт, вызов, разбор сырого JSON
    cli/                разбор аргументов, вывод обоих форматов, коды выхода, приёмник событий
  specs/                исполняемые спеки продуктового поведения
  schemas/              JSON-схемы публичного вывода
  evals/                сценарии оценки
  fixtures/             записанные ответы MCP-сервера + manifest.json
  tests/
  docs/
  probe.py              единственный файл с живой сетью
```

Поток данных линейный, в одну сторону:

```
аргументы CLI → Query (тип) → mcp: запрос → сырой JSON → разбор и валидация → Offer[] (типы)
             → правила core → отобранные Offer[] → рендер → stdout
```

### Правило зависимостей

- `core` не импортирует ничего из `cli`, `mcp`. Домен не знает про сеть, файлы и терминал.
- `mcp` импортирует `core` только ради типов результата.
- `cli` может импортировать всё.
- Обратных импортов нет.

Два следствия стоит назвать прямо. Бизнес-правило никогда не живёт в `cli`: если цена или дата
считается в обработчике аргументов или в шаблоне вывода — она в неправильном файле. И `core`
достижим тестами без единого мока — поэтому именно там доказывается правильность.

### Порядок реализации: изнутри наружу

Модуль пишется только тогда, когда всё, от чего он зависит, уже существует и зелено. Это
удерживает каждый слой тестируемым без моков.

**`core/`** (чисто, без I/O и часов):
`types` → `timing` → `price` → `parse-rules` → `events` → `filters` → `ranking` → `render`.

**`mcp/`**: `types` → `parse` → `transport` → `client` (кэш → повтор → запись/реплей).

**`cli/`**: аргументы → конверт вывода → коды выхода → приёмник событий.

Правила порядка:

- **Никогда не тянись вверх.** Если функции `core` нужно что-то, что умеет `mcp`, значение
  вычисляется в `cli` и передаётся аргументом.
- **Никогда не расширяй нижний слой ради удобства верхнего.** Добавь отображение в верхнем.
- Слой закончен, когда его тесты проходят без единого мока соседнего модуля проекта.

### Закрепление архитектуры тестами (обязательно)

Архитектура — это не картинка в README, а падающий тест.

- `tests/architecture/test_layers.py` — обходит импорты модулей (`ast`, stdlib) и падает при
  нарушении направления зависимостей.
- `tests/architecture/test_purity.py` — падает, если в `core` встречаются `open(`, `requests`,
  `httpx`, `socket`, `print(`, `datetime.now`, `date.today`, `time.time`, `os.environ`.
- `tests/architecture/test_boundaries.py` — падает, если `sys.exit` / `SystemExit` / `print`
  встречаются вне `cli`, и если `dict[str, Any]` встречается вне `mcp`.

Ослаблять их «на время» нельзя: правило либо есть, либо его нет.

## 6. Исполняемые спеки

Требование, которое нельзя запустить, — пожелание. Каждое продуктовое требование живёт в двух
неразделимых видах: формулировка на языке предметной области и спека, которая её проверяет.

- Спеки лежат в `specs/`, форма **Given — When — Then**, имя спеки — утверждение о поведении
  продукта («туда-обратно с пересадкой через полночь показывает верную дату прилёта»).
- Спека исполняется на записанных ответах MCP-сервера: без сети, без системных часов, без
  внешнего состояния.
- Раннер спек — несколько файлов внутри проекта поверх уже объявленного `pytest`, а не новый
  BDD-фреймворк (раздел 4). Табличные правила — время, отбор, ранжирование — пишутся через
  `parametrize` с именованными строками, чтобы сама спека читалась как формулировка алгоритма.
- Спека написана на языке путешественника и агента, не на языке кода. В тексте спеки нет имён
  функций, имён инструментов MCP и HTTP-глаголов.
  Плохо: `When search_avia called with origin=SVO`. Хорошо: `Когда ищем рейс из Москвы`.
- Новое поведение начинается со спеки: спека краснеет → код → спека зеленеет.
- Баг закрывается спекой, воспроизводящей его. Правка «на глаз» без спеки не считается
  исправлением.
- `specs/` — источник правды о поведении. Документы описывают систему, специфицируют её спеки.

### Спеки на честность — первого класса

Отсутствие данных, частичный отказ источника, цена без базы, неизвестная зона времени,
пустая выдача — это **заданное поведение со своей спекой**, а не краевой случай, который
обнаружится потом. Спека на честность пишется в том же пакете, что и спека на успех.

### Чего спеки не покрывают

Два класса вещей в спеки не попадают, и попытка их туда положить ломает правила выше.

**Протокольные и процессные пределы.** Ключи кэша, таймауты, число повторов, форма JSON-схемы,
побайтовое равенство — не то, что наблюдает путешественник. Это юнит- и контрактные тесты.
Спека формулирует наблюдаемое следствие: «тот же запрос на тех же записях отвечает так же,
не обращаясь к источнику».

**Всё, что требует живого MCP.** Это `tests/live/` под маркером `live`, вручную.

### Поверхность приёмки

Каждый сценарий продукта описан в `specs/` и исполняется офлайн. Таблица ниже — поверхность
приёмки продукта; **поведения, которого нет в таблице и нет в `specs/`, не существует.**
Добавляешь спеку — добавляешь строку в том же изменении. Соответствие таблицы и файлов на
диске проверяет `make docs-check`.

| Файл спеки | Что удерживает |
|---|---|
| `harness.py` | самопроверка обвязки: сеть закрыта, фикстуры сходятся с манифестом |
| `timing.py` | пояса, границы суток, длительности, ночной рейс |
| `price.py` | база цены, тарифное семейство, отсутствие цены |
| `parsing.py` | разбор 19 записей и четыре формы отказа |
| `filters.py` | правила отбора и событие на каждый отброшенный рейс |
| `ranking.py` | порядок и тай-брейк |
| `render.py` | оба формата на одних записях, побайтово |
| `contract.py` | форма конверта, типы ошибок, коды выхода |

### Скорость проверки — требование, а не удача

- Полный прогон спек — **не дольше 10 секунд** на ноутбуке. Прогон печатает скорость
  (`specs/sec`), чтобы деградация была видна сразу.
- Медленный прогон — дефект инструментария, а не норма: чинится распараллеливанием и удалением
  I/O из спек.
- Проверка, которую дорого запускать, перестаёт запускаться. Дешёвая проверка — то, ради чего
  весь остальной порядок и заводится.

### Запрос к данным

Агент обязан уметь проверить гипотезу о данных сам, не прося человека «посмотреть глазами»
и не вываливая файл в контекст.

- `make query` отвечает на вопрос к записанным ответам: сколько офферов, какие пересадки короче
  часа, какие сегменты пересекают полночь, у каких офферов нет цены.
- Ответ — компактная таблица или JSON, не дамп файла.
- Это инструмент разработки: он живёт в репозитории и описан в `docs/recordings.md`,
  но в `SKILL.md` его нет.

## 7. События: почему получился именно такой ответ

Пайплайн порождает поток событий. Событие — типизированный объект: что произошло, с чем и по
какому правилу. Такая система дешевле проверяется и позволяет ставить эксперименты, не трогая
остальное.

- **Каждое решение отбора оставляет событие.** Рейс отброшен — видно, какое именно правило его
  отбросило и с какими значениями.
- Часть событий приходит от сервера уже готовой (счётчики `post_filter_dropped_*`) — переносим,
  не изобретаем.
- `core` порождает события, но никуда их не пишет: приёмник внедряется как функция, по умолчанию
  «в никуда». Пишет их `cli`.
- События уходят в JSONL при `--trace <path>`. В stdout они не попадают никогда (раздел 10).
- Спеки утверждают про события, а не про внутренние вызовы: «рейс X отброшен правилом
  `max_connections`» — это проверяемое поведение, а не деталь реализации.
- Вопрос «почему в выдаче нет прямых рейсов» закрывается одним запуском с `--trace`, а не
  чтением кода.
- Замена одного правила отбора не должна требовать правок в остальном пайплайне. Если требует —
  правило прибито гвоздями не туда.

## 8. Данные и типы

- Между стадиями пайплайна — **только типизированные объекты**: `@dataclass(frozen=True, slots=True)`,
  `StrEnum`. Не словари.
- `dict[str, Any]` допустим **только** в двух точках: сразу после `json.loads` ответа MCP-сервера
  и прямо перед сериализацией итогового JSON.
- Валидация входа — **pydantic v2** на границе `mcp`, с
  `model_config = ConfigDict(strict=True, extra="forbid")`. Иначе `"5"` молча станет `5`,
  а переименованное поле сервера молча исчезнет.
- **У обязательных полей нет значений по умолчанию.** Отсутствие обязательного поля — явная
  типизированная ошибка, а не подставленный ноль.
- Одно имя поля = одно значение во всём пайплайне.
- Конвертация чисел из внешних данных — в одном модуле с явной обработкой некорректного ввода,
  а не по месту.
- `mypy --strict` на `src/` — зелёный. `# type: ignore` — только с комментарием, объясняющим причину.

### Отсутствие — это отсутствие

Правило, которое стоит дороже остальных в этом разделе, потому что нарушение выглядит как
рабочий код.

- **Ноль — это не «нет цены».** Оффер без цены обязан иметь `price = None`, а не ноль: ноль
  выигрывает любую сортировку по цене и проходит любой бюджетный фильтр. Измерено на том же
  сервере (Челябинск → Магнитогорск, 17.08.2026, `svyatrunov/tutu-compass`): электрички
  приходят с `price.amount: 0.0` и пустым списком перевозчиков.
- **Пустой список — это не «такого не бывает».** Пустая выдача при непустых счётчиках отказа
  или непустом `upstream_note` — частичный отказ источника, а не отсутствие рейсов.
- **Поле, которое есть в схеме и всегда пусто, хуже отсутствующего поля.** Если сервер обещает
  поле и не наполняет его, наш тип не обещает его тоже.
- Ничего не досочиняется, чтобы заполнить дыру: отсутствие доезжает до вывода как отсутствие.
  Значение из общих знаний вместо пришедшего от источника — запрещено.
- **Очевидный массив — не весь ответ.** Часть вариантов сервер прячет в `meta`; разбор обязан
  покрывать весь ответ, а не первое поле, которое выглядит как список.

### Прощающий вход, строгий выход

Аргументы приходят от агента, а агент присылает то, что присылает.

- Списочный аргумент принимается тремя формами: настоящим списком, строкой JSON и строкой через
  запятую. Числа в строках приводятся. Отсутствующий блок аргументов — пустой объект.
- Нормализация происходит один раз, на границе, до правил `core`; ключ кэша строится по
  нормализованной форме, чтобы все три формы попадали в одну запись.
- **Отклоняется только то, что нельзя понять.** Но ошибка ввода обязана назвать, какой параметр
  и чем именно плох, чтобы агент исправил запрос сам.
- Наружу уходит строго типизированный результат. Прощение работает только на входе.

## 9. Время, детерминизм, окружение

- Дата и время берутся **только** из внедряемого источника (`today: date`, `clock`).
  Прямой `date.today()` / `datetime.now()` / `time.time()` — **ровно в одной точке**, на входе CLI.
- Любой `datetime` — timezone-aware. Правило `DTZ` в ruff включено.
- Момент времени хранится дважды: aware `datetime` и местная строка от источника. Длительности
  считаются по моментам, «ночной рейс» — по местному времени. Вся арифметика в `core/timing.py`.
- Таймзоны сегментов берутся из данных источника. Таймзона прилёта не равна таймзоне вылета,
  пока данные не сказали обратного.
- **В спеках и тестах запрещены «живые» даты.** Опорное «сегодня» задаётся явно — в спеках
  и в режиме `replay` им служит `recorded_at` из конверта записи (раздел 12). Спека, зелёная
  сегодня и красная через месяц, считается сломанной сразу.
- Один и тот же запрос на одних и тех же записях даёт побайтово один и тот же ответ.
- Адрес MCP-сервера, таймауты, ключи — из конфига и переменных окружения, не зашиты в код.
- Секреты не попадают в stdout, логи, сообщения об ошибках, события и записанные снапшоты.
  В снапшотах они заменяются на маркер **при записи**, а не при чтении.

## 10. Контракт с агентом

### 10.1. Вывод

```json
{"ok": true,  "command": "search", "data": {...}, "issues": []}
{"ok": false, "command": "search", "error": {"type": "...", "message": "...", "retryable": false, "details": {...}}}
```

- Поле ошибки называется `type`. Типы ошибок — `StrEnum`, закрытый задокументированный список.
  `retryable` говорит агенту, имеет ли смысл повтор; свободный текст `message` — для человека,
  решения по нему не принимаются.
- Форма ответа **одна и та же всегда**, включая ошибки. Агент не должен разбирать разные структуры.
- Частичный отказ — типизированный `Issue` в `issues`, а не пустой список и не молчание.
- В stdout — **только** JSON, один объект. Диагностика, прогресс, предупреждения — в stderr,
  события — в файл `--trace`.
- Коды выхода фиксированы и задокументированы.
- Схема лежит в `schemas/`, проверяется тестом через `jsonschema`. Контракт расширяется только
  под конкретную потребность.

### 10.2. Эргономика для агента

Агент платит контекстом за каждый байт вывода и не умеет переспрашивать утилиту.

- CLI **никогда не интерактивен**: не читает stdin, не ждёт подтверждений, не печатает
  прогресс-бары в stdout.
- Объём вывода ограничен: по умолчанию N лучших вариантов (`--limit`, дефолт 10), полей —
  минимум необходимого. «Отдать всё, агент разберётся» — запрещено.
- Порядок результатов детерминирован, тай-брейк при равной цене задокументирован.
- `--help` и `--schema` дают машинно-читаемое описание параметров и ответа, чтобы агент не гадал.
- Управляющие указания агенту в `data` не кладутся. Инструкция агенту живёт в `SKILL.md`,
  данные — в `data`.

### 10.3. Ошибки

- Один способ сообщить об ошибке на весь проект.
- Библиотечный код не вызывает `sys.exit` и не печатает в stdout. Завершение процесса — только
  в `main()`.
- `except Exception` — только на внешней границе CLI, где ошибка превращается в envelope.
- Исключение не гасится подстановкой «безопасного» значения. Ошибка MCP-сервера видна в ответе
  как именованная ошибка.
- **Неудача источника — ограничение доступа к данным, а не доказательство отсутствия факта.**
  «Не смогли получить данные» ≠ «рейсов нет», и агент различает это по `type`. Сказать «рейсов
  нет» можно только когда список пуст, счётчики отказов нулевые и `upstream_note` пуст.
- Сервер отвечает кодом 200 на все формы отказа; JSON-RPC `error` не приходит никогда. Успех
  отличается от отказа по `result.isError` и счётчикам, а не по префиксу текста.

## 11. SKILL.md

Обязательный frontmatter:

```yaml
---
name: tutu-search-flights
description: "Use when ... — что делает и когда применять, третьим лицом, ≤1024 символов"
version: "0.1.0"
author: Hermes Agent
license: MIT
metadata:
  hermes:
    category: travel
    tags: [...]
    requires_toolsets: [terminal]
---
```

- **Версия объявлена ровно в одном месте — `pyproject.toml`.** В коде читается через
  `importlib.metadata.version`, в `SKILL.md` проставляется командой `make version-sync`.
  Руками версия не дублируется и по файлам не разносится.
- `description` — всегда «Use when …» с триггерными словами. Императив («Search flights»)
  не срабатывает при выборе скилла.
- Тело ≤ 500 строк, прогрессивное раскрытие: подробности — в `references/`, на один уровень вглубь.
- Инструкции по разработке и сопровождению в `SKILL.md` не живут — они съедают контекст на каждом
  запуске. Их место: `references/*-maintenance.md`.
- Раздел Dependencies объявляет каждую внешнюю зависимость рантайма (Python, MCP-сервер, утилиты).
- Скилл запускается одной командой из своего корня: без ручного `PYTHONPATH`, без
  «сначала установи вот это».
- Никаких дат в примерах команд — они устаревают.
- Одна терминология на весь скилл: одно понятие — одно слово. Те же слова стоят в README,
  в `docs/`, в именах типов и в тексте ошибок.
- **Скилл живёт только внутри своей папки.** Исходники агента, его тесты и allowlist'ы скилл
  не трогает. Нужна поддержка со стороны рантайма — это отдельная задача в рантайме.

## 12. Записи ответов MCP-сервера

Основа всего: спеки, юниты, e2e и режим `replay` читают отсюда. Сеть в остальном репозитории
запрещена фикстурой, ломающей сокет.

Живая сеть разрешена **ровно одному файлу** — `probe.py`. Через него работают обе
съёмочные команды: `make discover` снимает фактическую спецификацию инструментов сервера
в `docs/mcp-notes.md`, `make record` пересобирает записи в `fixtures/`. Больше живых вызовов
в репозитории нет, и это проверяет `tests/architecture/test_purity.py`.

### Запись — это конверт, а не голый ответ

```json
{
  "recorded_at": "2026-09-14T09:41:22Z",
  "tool": "search_avia",
  "arguments": { "origin": "KGD", "destination": "VVO", "date": "2026-10-02" },
  "server_version": "0.51.0",
  "note": "зачем существует этот файл: три пояса и переход через полночь",
  "volatile": ["offers[].checkout_ref", "meta.search_id"],
  "response": { "envelope": { ... }, "payload": { ... } }
}
```

- **`recorded_at` — опорное «сегодня» в режиме `replay`.** Без него записанный рейс через неделю
  молча становится прошедшим, отбор начинает его выбрасывать, и набор краснеет сам, обвиняя
  ядро в ошибке календаря.
- **`volatile` перечисляет то, что протухает**: `checkout_ref`, `search_id`, готовые ссылки.
  Эти поля годятся для проверки разбора и **никогда** не проверяются на работоспособность,
  не кэшируются и не выдаются как живые.
- **`response.envelope` — сырой кадр MCP, `response.payload` — JSON, который сервер прячет
  строкой внутри текстового блока.** Хранятся оба: конверт — то, что должен пережить клиент,
  payload — то, что читают тесты.
- `note` объясняет, зачем файл существует. Запись без причины — мусор, который никто не решится
  удалить.
- `fixtures/manifest.json` связывает каждый файл с породившим его запросом и датой снимка.
  `specs/harness.py` сверяет манифест с содержимым каталога и падает при расхождении.

### Как записи именуются и откуда берутся

- Имя — по **роли**, а не по городу и не по хэшу: `three-timezones.json`, `empty-result.json`,
  `upstream-degraded.json`, `fare-family.json`. Роль переживает смену маршрута, город — нет.
- `make record` пересобирает записи, задавая серверу **те вопросы, которые задаёт сам продукт**:
  скрипт вызывает построитель запроса из `core`, а не зашитые аргументы. Запись, снятая на
  вопросы, которых продукт не задаёт, приводит к тому, что `replay` отказывает на каждом
  обращении и выглядит при этом ровно как недоступность сервера.
- Режим переключается одной переменной: `TUTU_SEARCH_FLIGHTS_MODE=live|replay|record`.
  По умолчанию `replay`. Третьего режима сервера нет — запись это скрипт, а не режим работы.
- Секреты вырезаются на этапе записи.
- **Запись — данные, а не код: руками не редактируется.** Изменилось поведение сервера —
  перезаписываем и разбираем разницу.
- Живые тесты — под маркером `@pytest.mark.live`, выключены по умолчанию, в CI не гоняются.

### Обязательный минимум записей

Не менее пяти, и среди них обязательно: успешная выдача, пустая выдача, ошибка сервера,
частичный отказ (непустые счётчики при пустом списке) и перелёт через границу суток
с тремя поясами. Каждая — с `note`, объясняющей, что именно она доказывает.

### Три слоя клиента, в этом порядке

`кэш → повтор с бэк-оффом → запись/реплей`. Порядок важен: в `replay` соединение не
открывается вообще, и весь набор проверок работает без интернета.

## 13. Тесты и ворота качества

### 13.1. Что проверяют тесты

- Имя теста — утверждение о поведении, а не имя функции.
- Тест не знает про внутреннее устройство и **не мокает внутренние модули проекта**.
  Мокать разрешено только внешнюю границу — транспорт MCP.
- Проверяется результат и порождённые события, а не порядок внутренних вызовов.
- **Утверждай про значения, а не про формы.** `assert total == 14705` лучше, чем `assert total > 0`.
- **Фикстуры типизируются на входе.** Тест утверждает про нормализованный доменный тип, а не про
  сырой JSON Туту: изменение их ответа ломает один модуль, а не пятьдесят тестов.
- Фабрики тестовых объектов — в `tests/factories`, не в теле теста.
- Тесты герметичны: без сети, без системных часов, `tmp_path` вместо фиксированных путей.
- Удаляя публичное поведение, удаляй его спеки в том же изменении и добавляй позитивные спеки
  нового.

### 13.2. Уровни

| Уровень | Где | Что проверяет |
|---|---|---|
| Архитектурные | `tests/architecture/` | направление зависимостей, чистота слоёв (раздел 5) |
| Спеки | `specs/` | продуктовое поведение: время, цена, отбор, ранжирование, рендер, события |
| Контрактные | `tests/contract/` | разбор записанных ответов; JSON-схема вывода; стабильность полей |
| E2E | `tests/e2e/` | запуск настоящей команды через `subprocess`: stdout, stderr, код выхода, оба формата |
| Живые | `tests/live/` | реальный MCP-сервер, маркер `live`, вручную |

E2E обязателен для MVP: успешный поиск, пустая выдача, ошибка сервера, некорректный ввод.
Отдельный e2e проверяет, что при `--format json` в stdout нет ничего, кроме JSON.

### 13.3. Обязательный набор утверждений

Каждый пункт — дефект, который уже наблюдался на этом сервере или отстоит от него на один ответ.
Список живёт здесь целиком, потому что он и есть содержание приёмки.

1. Цена группы не умножается на число пассажиров.
2. Цены с разной базой не складываются — это ошибка типа, а не число.
3. `price` оффера — нижняя граница тарифного семейства, и вывод это называет.
4. Оффер без цены не участвует в сортировке по цене и не проходит бюджетный фильтр.
5. Дата прилёта считается в поясе прилёта; перелёт KGD → SVO → VVO приходит на следующий день.
6. Время с обеденным смещением не переезжает на соседние сутки по дороге через UTC.
7. Длительность считается по моментам, «ночной рейс» — по местному времени.
8. Пустой список при ненулевых счётчиках отказа не превращается в «рейсов нет».
9. Каждая из четырёх форм отказа даёт свой `type` и своё значение `retryable`.
10. Каждый отброшенный рейс оставляет событие с именем правила и значениями.
11. Равные цены разводятся стабильным вторичным ключом.
12. Один и тот же запрос на одних записях даёт побайтово один и тот же вывод обоих форматов.
13. Эквивалентные формы аргумента дают один ключ кэша.
14. В режиме `replay` опорная дата — `recorded_at`, а не системные часы.
15. `--limit` ограничивает вывод, и превышение не «протекает» в text-формат.

### 13.4. Мутационные тесты

Спека, которая ничего не утверждает, выглядит как зелёная. Мутационный прогон — единственный
способ это заметить.

- Инструмент: `mutmut`, цель — `core/` и разбор ответов в `mcp/`.
- Порог MVP: **mutation score ≥ 70 %**, дальше ≥ 80 %.
- Запуск не на каждом коммите: `make mutants` и отдельный job в CI по изменённым файлам.
- Выживший мутант закрывается **новой спекой**, а не исключением в конфиге. Исключение — только
  с комментарием, почему мутант эквивалентен.

### 13.5. Eval-сценарии

- `evals/*.yaml`: вход (параметры + имя записи), ожидаемое поведение, чего быть не должно.
- Минимум 5 сценариев для MVP: обычный туда-обратно; только прямые; выдача пуста; ошибка сервера;
  некорректный ввод.
- Отдельный сценарий проверяет **вызов скилла агентом**: по `SKILL.md` агент выбирает команду,
  собирает аргументы и корректно читает ответ.
- **Каждый сценарий несёт строку о том, из какого наблюдённого отказа он родился.** Сценарий без
  такой истории — это тест, а не eval; ему место в `tests/`.
- Прогон одной командой `make evals`, результат — таблица «сценарий / прошёл / что разошлось»,
  ненулевой код выхода при первом расхождении.
- Скилл без evals считается непроверенным.

### 13.6. Definition of Done — машинные ворота

Задача не закрыта, пока `make check` не прошёл **и его вывод не показан**. `make check` — это ровно:

```bash
uvx ruff check .
uvx ruff format --check .
uv run mypy --strict src
uv run pytest -q                    # архитектурные, контрактные, e2e
uv run pytest -q specs              # исполняемые спеки, печатает specs/sec
uv run radon cc -s -n C src         # сложность выше порога — пустой вывод
make docs-check                     # команды из документов существуют; таблица спек сходится
```

Перед релизом версии дополнительно: `make mutants`, `make evals`.

- Красные тесты, `F401`, невыполненный `format --check` — невыполненная задача, а не мелочь.
- Мёртвый код (`F401`, `F841`) удаляется сразу.
- Ни `TODO`, ни закомментированного кода, ни заглушки, которая возвращает правдоподобное
  значение.
- Ни одной заявленной в документах возможности, которой нет в коде.
- CI гоняет ровно `make check`. Локально и в CI — одни и те же команды. Нет CI — нет приёмки.

## 14. Дерево документов и его пополнение

Документация — рабочий инструмент агента, а не отчёт о проделанной работе. Она устроена деревом:
сверху короткий навигатор, вглубь — детали. Агент читает **только нужную ветку** и не тратит
контекст на остальное.

| Файл | Что внутри |
|---|---|
| `AGENTS.md` | навигатор: одна страница, что где лежит, куда идти за чем |
| `PROJECT_RULES.md` | этот документ: правила и их машинные проверки |
| `README.md` | что это, установка, три исполняемых примера, оба формата вывода, ограничения |
| `docs/architecture.md` | слои, правило зависимостей, поток данных, события |
| `docs/contract.md` | JSON-схема вывода, типы ошибок, `retryable`, коды выхода |
| `docs/mcp-notes.md` | фактическая — не заявленная — спецификация сервера и измеренные ловушки |
| `docs/recordings.md` | как записать и перезаписать ответ, что вырезается, как делать запрос к данным |
| `docs/edge-cases.md` | краевые случаи и что с ними делает система |
| `docs/decisions.md` | решения: контекст, решение, следствие, статус |
| `docs/plans/` | планы текущих задач; после выполнения удаляются, знание переезжает выше |
| `CHANGELOG.md` | semver, запись на каждое изменение публичного поведения |

- Каждый документ ≤ 200 строк. Больше — делится на ветку.
- Ссылки идут вниз по дереву, а не вбок: документ не пересказывает соседний.
- В README обязателен раздел ограничений — списком и честно. Возможности, которой нет в коде,
  в документах не бывает.
- В поставку скилла планы и аудиты не попадают.

### Журнал решений

Запись появляется только тогда, когда была **отвергнутая альтернатива и заплаченная цена**.
Выбор имени, версия Python и заготовка файла решениями не являются; журнал не заводится под
пустые слоты.

У записи четыре части: контекст, решение, следствие, **статус**. Статус говорит, что из записи
уже живёт в коде, а что пока только решено, — и делает запись проверяемой по репозиторию,
а не принимаемой на слово.

### Пополнение — часть каждой задачи, а не отдельный проект

Задача не закрыта, пока то, что выяснилось по дороге, не легло в дерево:

- новый краевой случай → `docs/edge-cases.md` + спека;
- новая находка о поведении сервера → `docs/mcp-notes.md` + запись в `fixtures/` с `note`;
- принятое решение или сознательно отвергнутый вариант → запись в `docs/decisions.md`;
- изменение публичного поведения → `docs/contract.md` + `CHANGELOG.md` + строка в таблице
  поверхности приёмки;
- бизнес-константа → значение + причина + источник и дата, рядом с константой.

`make docs-check` исполняет примеры команд из README, падает при расхождении вывода, падает,
если документ называет несуществующую цель `Makefile`, и падает, если таблица поверхности
приёмки разошлась с файлами в `specs/`. Документ, который нельзя проверить командой, устаревает
молча — и следующий запуск агента начнётся с неверной картины.

## 15. Control center

Одна точка входа во все действия проекта. Агент не изобретает команды и не держит их в голове.

- `Makefile` — единственный список команд: `make check`, `make specs`, `make e2e`, `make record`,
  `make discover`, `make query`, `make evals`, `make mutants`, `make docs-check`,
  `make version-sync`.
- Повторяющаяся последовательность действий превращается в цель `Makefile` в тот же день, а не
  в абзац инструкции. Инструкция, которую надо выполнять руками, будет выполнена неправильно.
- Команда, названная в документе, обязана существовать — это проверяет `make docs-check`,
  а не внимательность.
- Обвязка проекта даёт накопительный эффект: каждый следующий запуск агента дешевле, быстрее
  и спокойнее для проверки. Экономить на обвязке — значит платить за неё каждый раз заново.

## 16. Сложность

- Цикломатическая сложность функции ≤ 12 (`radon cc -s -n C`, входит в `make check`).
- Файл > 400 строк — делим по ответственности. Признак к делению появляется уже около 300.
- Функция с > 5 позиционными параметрами переводится на объект-параметр.
- Числовые пороги в сравнениях выносятся в именованные константы с обоснованием.
- Дублирование устраняется только когда оно реально разошлось в поведении. DRY ради DRY запрещён.

## 17. Стоп-сигналы

Остановись и переспроси, если собираешься:

- принести фичу целиком вместо следующего проверяемого шага;
- добавить слой или абстракцию, ничего не удалив;
- написать документ вместо кода («задокументировать проблему» вместо исправления);
- ослабить архитектурный тест или спеку, чтобы код прошёл;
- поправить спеку под текущее поведение вместо исправления поведения;
- отредактировать записанный ответ сервера руками;
- подставить ноль, пустой список или значение по умолчанию там, где источник ничего не дал;
- добавить мутанта в исключения вместо спеки;
- добавить запрет в `SKILL.md`, чтобы обойти неудобный вывод CLI;
- обернуть падение в `try/except` с дефолтом, чтобы «прошло»;
- написать спеку на языке кода вместо языка предметной области;
- ответить «должно работать» без запуска;
- начать переписывать модуль, который не входил в задачу;
- расширить область MVP из раздела 2.

## 18. Готовность MVP

Версия 0.1 готова, когда одновременно верно:

1. Агент по `SKILL.md` вызывает `search`, получает JSON и отдаёт человеку текстовый блок без
   переписывания.
2. `make check` зелёный, вывод показан.
3. Архитектурные тесты существуют и падают при искусственном нарушении правил (проверено вручную).
4. Полный прогон спек укладывается в 10 секунд, скорость напечатана.
5. Есть не менее пяти записей из обязательного минимума раздела 12, каждая с `note`, и манифест
   сходится с каталогом.
6. E2E покрывают четыре сценария из 13.2 плюс чистоту stdout.
7. Все пятнадцать утверждений раздела 13.3 закреплены спеками.
8. `--trace` объясняет, почему каждый отброшенный рейс отброшен, и на этом объяснении стоит
   минимум одна спека.
9. Mutation score по `core/` ≥ 70 %.
10. 5 eval-сценариев проходят, включая сценарий вызова агентом.
11. `AGENTS.md`, `README.md`, `docs/architecture.md`, `docs/contract.md` соответствуют коду,
    `make docs-check` это подтверждает, и таблица поверхности приёмки сходится с `specs/`.
