# Правила проекта tutu-search-flights

## Факты прежде предположений

Перед изменением изучи относящиеся к задаче research (`docs/mcp-notes.md`), fixtures, текущую product specification, существующий код и тесты. Не придумывай возможности Tutu MCP или устройство продукта.

## SDD

Для нового продуктового поведения:
1. Определи ожидаемое наблюдаемое поведение.
2. Свяжи его с executable specification.
3. Получи RED по правильной причине.
4. Реализуй минимально необходимое.
5. Получи GREEN.
6. Выполни общие проверки.

Для существующего контракта усиливай утверждения против наблюдаемого результата,
сохраняя широту требования; не подменяй проверку копией целого expected-преобразования.
Связывай каждое требование с test node ID и его фактическим охватом в
docs/verification.md. Непроверенные варианты помечай partial или deferred.

Не пиши реализацию раньше соответствующего требования.

## Tests

Тест защищает конкретное поведение, публичный контракт или реальный дефект. Не создавай архитектурные тесты ради предполагаемой архитектуры.

## Research

Для исследования и обновления fixtures используется `probe.py`. Production live-search идёт через MCP SDK client. Обычные specs/tests работают на записанных данных. Raw fixtures вручную не редактируются.

## Architecture

Не проектируй слои и абстракции заранее. Добавляй структуру только когда она нужна существующему поведению и упрощает реализацию.

## Evaluate

Оценка поведения агента выполняется внешним общим evaluate harness и не является частью этого skill. Evaluate не смешивается с production skill и его tests.

## Проверка

Не заявляй о работоспособности без реально выполненной команды проверки.
Записывай точную границу результата: targeted tests, полный локальный gate,
live integration, remote CI и внешний agent evaluation — отдельные проверки.
