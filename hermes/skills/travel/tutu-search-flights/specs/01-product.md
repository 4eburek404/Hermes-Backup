# Продукт

Спецификация версии 0.1. Источник правды о том, что продукт обещает.
Всё, что здесь написано, опирается на разведку живого сервера — см.
[`../docs/mcp-notes.md`](../docs/mcp-notes.md), снято 14.09.2026.

## Задача

Агенту Hermes нужно ответить человеку на вопрос про перелёт: есть ли рейсы, сколько
стоят, что с багажом, во сколько лететь. Сегодня агент ходит к источнику сам и каждый
раз по-своему: то умножает цену на число пассажиров, то называет пустую выдачу
отсутствием рейсов, то считает длительность по часам на табло.

Скилл закрывает это одной командой: агент вызывает CLI, получает строгий JSON и готовый
текстовый блок для человека. Решения об отборе, цене и времени принимает код, а не модель.

## Сквозной сценарий

> Человек спрашивает у агента: «найди билеты Москва — Сочи на 15 октября, без пересадок,
> до 10 тысяч». Агент вызывает `search` с этими параметрами. CLI опрашивает Tutu MCP,
> разбирает ответ, применяет правила отбора, ранжирует и печатает: агенту — JSON
> фиксированной формы, человеку — блок текста, который агент отдаёт как есть.

## Вход и выход

```
Вход:   откуда, куда, дата вылета, дата возврата (необязательно),
        состав пассажиров, класс, ограничения отбора

Выход:  {"ok": true,  "command": "search", "data": {...}, "issues": [...]}
        {"ok": false, "command": "search", "error": {...}}
```

Форма ответа одна и та же всегда, включая ошибки. Агент не разбирает разные структуры.

Отсутствующее поле остаётся отсутствующим до самого вывода. Не заменяется нулём,
не угадывается, не добирается из общих знаний о перевозчике.

## Правила, которые считает код

### Цена

Цена приходит за **всю запрошенную группу** — сервер сообщает это в `meta.pricing.basis`
(`party_total`) и отдельной строкой предупреждает не умножать её на число пассажиров.

Измерено на рейсе `DP-6941` 15.10.2026:

| Запрос | Цена |
|---|---|
| 1 взрослый | 5 863 ₽ |
| 2 взрослых + ребёнок | 14 705 ₽ |

Умножение дало бы 17 589 ₽ — ошибка в 2 884 ₽ и ложный вывод «не влезаем в бюджет».

У рейса не одна цена, а тарифное семейство. Тот же `DP-6941`:

| Тариф | Цена | Багаж | Возврат |
|---|---|---|---|
| Базовый | 5 863 | 0 кг | нет |
| Выгодный | 8 662 | 10 кг | нет |
| Максимум | 11 992 | 20 кг | да |

**Продукт никогда не называет цену без базы и без тарифа.** «Перелёт за 5 863» без
оговорки про ноль килограммов багажа — то же враньё, что выдуманное поле.

### Время

Все моменты приходят со смещением: `2026-10-15T16:50:00+03:00`. Одно предложение может
пересекать несколько поясов и границу суток. Живой пример из фикстуры `connections.json`:

```
SU-1017  Калининград (+02:00) 11:35  →  Шереметьево (+03:00) 15:10   15 октября
SU-5804  Шереметьево (+03:00) 18:25  →  Владивосток (+10:00) 09:45   16 октября
```

Итого 655 минут. По часам на табло «с 11:35 до 09:45» — бессмыслица.

```
длительность и стыковка  → только по разнице моментов
«ночной рейс», «день вылета» → только по местному времени вылета
```

Перевод в UTC перед вопросом «утро или вечер» запрещён: он превращает утренний рейс
в дневной и отправляет человека на день позже.

### «Нет рейсов» против «не смогли узнать»

Сервер отвечает кодом 200 на все четыре случая, и `error` по протоколу не приходит
никогда. Различать обязательно:

| Что случилось | Как распознать |
|---|---|
| ошибка ввода | `isError: true`, текст не JSON |
| источник не знает маршрут | `isError: true`, текст с подсказкой альтернативы |
| выдача пуста, объяснил апстрим | `offers: []`, заполнен `upstream_note` |
| выдача пуста, отсёк наш фильтр | `offers: []`, `post_filter_dropped_* > 0` |

**Сказать «рейсов нет» можно только когда список пуст, все счётчики `post_filter_dropped_*`
нулевые и `upstream_note` пуст.** Во всех остальных случаях продукт говорит, чего именно
он не смог узнать, и почему.

Проверено: запрос с `carriers: ["aeroflot"]` латиницей вернул пустой список при
`post_filter_dropped_wrong_carrier: 22` — фильтр отбросил все рейсы, а выглядело это как
отсутствие рейсов.

### Отбор

Каждое отброшенное предложение оставляет событие: какое правило, с какими значениями.
Часть событий приходит от сервера готовой (`post_filter_dropped_not_direct`,
`_wrong_carrier`, `_wrong_airport`, `_wrong_flight_number`) — их не изобретаем, а
переносим. Свои события заводим только на правила, которые применяем сами.

Вопрос «почему в выдаче нет прямых» закрывается одним прогоном с `--trace`.

### Порядок

Детерминированный. При равной цене — стабильный вторичный ключ: длительность, затем
число пересадок, затем идентификатор предложения. Один и тот же запрос на одних и тех же
записях даёт побайтово один и тот же ответ.

## Состояния и честность

| Ситуация | Что показывает продукт |
|---|---|
| источник не ответил | «не смогли получить», а не «рейсов нет» |
| поле отсутствует | блок скрыт, а не заполнен догадкой |
| пересадка отдельными билетами | предупреждение из `multi_pnr_note`, багаж переоформляется |
| страница не последняя | «показаны N из M», а не «это всё» |
| вход не разобран | какой параметр и чем именно плох |

## Три вещи, которые нельзя резать

Написано до начала работы и не пополняется по ходу.

1. **База цены и тариф.** Без них цена неверна, а продукт существует ради цены.
2. **Различение «нет» и «не смогли узнать».** Это единственное, что отличает честный
   ответ от уверенного вранья, и данные для него уже есть в ответе сервера.
3. **Время по моментам.** Три пояса в одном перелёте — обычный трансфер через Москву,
   а не экзотика.

## Чего в версии 0.1 нет

| Не делаем | Почему |
|---|---|
| бронирование (`register_checkout_passengers`) | создаёт реальный неоплаченный заказ и требует паспортных данных |
| кэш | сеть в разработке и тестах заменена записями, эффект уже получен |
| второй источник | один источник — обещание архитектуры, не ограничение |
| мультигород, сложные тарифные правила | объём |
| вторая команда | одна команда `search` |

## Готовность 0.1

1. Агент по `SKILL.md` вызывает `search`, получает JSON и отдаёт человеку текстовый блок
   без переписывания.
2. `make check` зелёный, вывод показан.
3. Архитектурные тесты падают при искусственном нарушении правил — проверено руками.
4. Каждая из 19 записанных фикстур либо разбирается, либо даёт типизированный `Issue`.
5. Ни один ответ не называет пустую выдачу отсутствием рейсов, если счётчики отбора
   ненулевые.
6. `--trace` объясняет, почему отброшен каждый рейс, и на этом стоит минимум одна спека.
7. Цена нигде не показана без базы и тарифа.
