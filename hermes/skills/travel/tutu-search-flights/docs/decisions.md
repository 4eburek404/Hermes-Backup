# Журнал решений

## 1. Research записан до product code

**Контекст.** Типы, основанные на предположении о формате ответа, пришлось бы пересматривать после живого вызова.

**Решение.** До продуктового кода исследовать Tutu MCP, сохранить ответы в fixtures и зафиксировать наблюдения в `docs/mcp-notes.md`.

**Следствие.** Product specifications опираются на записанные наблюдения. Fixtures используются как фактическая база для будущих офлайн-проверок.

**Статус.** Действует.

---

## 2. Архитектурные ворота до product code — заменено

**Контекст.** Ранее предполагалось закрепить архитектуру и её ограничения тестами до реализации продукта.

**Прежнее решение.** Архитектурные тесты и фиксированная структура слоёв должны предшествовать продуктовому коду.

**Статус.** Заменено: преждевременно закрепляло устройство продукта без подтверждённой необходимости.

### Действующее решение

До продуктовой реализации создаются проверки сохранности research и fixtures. Архитектурные ограничения добавляются только тогда, когда появляется обоснованная архитектура.

**Следствие.** Текущие проверки защищают фактические записи и их manifest; они не предписывают будущую архитектуру.

**Статус.** Действует.

---

## 3. Типизированный поток данных поиска

**Дата:** 24.09.2026  
**Статус:** действует.

### Контекст

Исторический контекст на дату решения (24.09.2026): первая executable
specification поиска была зафиксирована и находилась в RED, рабочей реализации
тогда ещё не было. Это объясняет исходный выбор типа данных и не описывает нынешний
статус реализации.

Tutu MCP возвращает JSON-RPC envelope, внутри которого результат `search_avia` передаётся как JSON в текстовом content-блоке. Фактическая структура ответа исследована и сохранена в fixtures: `offers`, `legs`, `segments`, `variants`, `conditions`, `meta`.

Требование к реализации: после разбора внешнего ответа данные между частями production-поиска должны передаваться как типизированные объекты, а не как произвольные словари.

### Рассмотренные варианты

#### Вариант A — типизированная модель, повторяющая фактический ответ Tutu

После внешней JSON-границы ответ Tutu валидируется в типизированные модели, соответствующие фактической структуре источника:

`SearchResponse -> Offer -> Leg -> Segment`

и

`Offer -> Variant -> Conditions`.

**Плюсы:**
- один переход из внешнего JSON в типизированные данные;
- минимум дополнительного кода и преобразований;
- низкий риск потерять или исказить данные источника;
- изменения структуры Tutu обнаруживаются при валидации;
- fixtures напрямую сопоставимы с моделями;
- не требуется заранее проектировать собственную модель авиации.

**Минусы:**
- код продукта остаётся связан с формой ответа Tutu;
- особенности Tutu могут проникать в последующую логику;
- при появлении другого провайдера общей модели пока не будет.

#### Вариант B — Tutu DTO + отдельная provider-independent domain model

Ответ Tutu сначала валидируется в типы источника, затем преобразуется в собственные `FlightOption`, `Fare`, `Money` и другие сущности продукта.

**Плюсы:**
- бизнес-логика меньше зависит от Tutu;
- удобнее объединять несколько провайдеров;
- внутреннюю модель можно оптимизировать под собственные алгоритмы.

**Минусы:**
- появляется второй набор моделей и отдельное преобразование;
- возникает дополнительное место для потери `None`, цен, тарифных условий, пагинации и других фактов;
- нужно заранее определить понятия и границы domain model, которых текущие executable specifications ещё не требуют;
- сложность первой реализации увеличивается без подтверждённой пользы.

#### Вариант C — TypedDict

Отклонён. Он даёт статические подсказки, но runtime-данные остаются обычными словарями, доступ сохраняется через `["field"]`, а входной ответ MCP сам по себе не валидируется.

#### Вариант D — генерация типов из MCP schema

Сейчас не подходит как основной путь. `tools/list` формально описывает вход `search_avia`, но богатая структура результата приходит как JSON внутри text content и не имеет достаточной output schema для генерации всей модели результата.

### Решение

Для первой реализации использовать **типизированную модель, повторяющую фактический ответ Tutu**, без отдельного provider-independent domain layer.

Поток данных:

```text
MCP / JSON
    ↓
parse + validation
    ↓
typed Tutu models
    ↓
product behavior
```

Не вводится общий запрет на использование `dict`. Правило относится к **контрактам между частями production-поиска**: после разбора ответа Tutu рабочие данные не должны передаваться между этапами как произвольные словари.

Словари допустимы там, где этого требует формат внешней границы или вспомогательный код, например:
- чтение и запись JSON;
- аргументы и сырой ответ MCP;
- тестовый адаптер;
- локальные технические структуры, не являющиеся контрактом между этапами поиска.

Для runtime validation использовать Pydantic-модели. Они должны отражать фактическую структуру Tutu и не вводить новые предметные абстракции без необходимости.

Денежное `amount` после разбора представляется точным числовым типом (`Decimal`), а не `float`. Даты и время разбираются в timezone-aware `datetime`, когда соответствующее поле присутствует в ответе.

Текущие словари в executable specification остаются языком наблюдений теста и не задают внутреннюю архитектуру production-кода. При необходимости `tests/product_driver.py` адаптирует типизированный результат продукта к форме наблюдений теста.

### Почему

Сейчас задача — корректно реализовать один источник по уже записанному фактическому контракту. Отдельная domain model пока не решает подтверждённую проблему, но создаёт дополнительное преобразование и новые архитектурные решения.

Типизированная модель источника устраняет неструктурированный поток словарей с минимальным объёмом новой архитектуры и соответствует принятому порядку разработки: сначала наблюдаемое требование и executable specification, затем минимальная реализация.

### Когда пересмотреть

Отдельная provider-independent модель становится обоснованной, если executable specification потребует хотя бы одно из следующего:

- объединять результаты Tutu с другим провайдером;
- применять общее поведение к данным разных форматов;
- существующая структура Tutu объективно мешает реализации требуемого алгоритма;
- повторяющиеся преобразования показывают устойчивую собственную предметную модель.

До появления такого требования дополнительный domain layer не вводится.
