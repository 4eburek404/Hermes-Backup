# Решение: типизированный поток данных поиска

**Дата:** 24.09.2026  
**Статус:** принято

## Контекст

Первая executable specification поиска уже зафиксирована и пока находится в RED: рабочей реализации поиска нет.

Tutu MCP возвращает JSON-RPC envelope, внутри которого результат `search_avia` передаётся как JSON в текстовом content-блоке. Фактическая структура ответа исследована и сохранена в fixtures: `offers`, `legs`, `segments`, `variants`, `conditions`, `meta`.

Нужно реализовать поиск так, чтобы рабочий поток данных внутри продукта был типизированным. Передача данных между этапами через произвольные `dict` не принимается.

При этом текущие product specifications не требуют общей модели авиаперелётов, нескольких провайдеров или отдельного domain layer. Правила проекта запрещают заранее закреплять архитектуру без подтверждённой необходимости.

## Рассмотренные варианты

### 1. Типизированная модель, повторяющая фактический ответ Tutu

После внешней JSON-границы ответ Tutu валидируется в типизированные модели, соответствующие фактической структуре источника:

`SearchResponse -> Offer -> Leg -> Segment`

и

`Offer -> Variant -> Conditions`.

Поля сохраняют семантику Tutu. Например, `voyage_no`, `pricing.basis`, `post_filter_dropped_*`, `upstream_note` не переосмысливаются заранее.

**Плюсы:**
- один переход из внешнего JSON в типизированные данные;
- минимум дополнительного кода и преобразований;
- низкий риск потерять или исказить данные источника;
- изменения структуры Tutu обнаруживаются при валидации;
- fixtures напрямую сопоставимы с моделями;
- соответствует текущей SDD-стадии и не проектирует будущую архитектуру заранее.

**Минусы:**
- код продукта остаётся связан с формой ответа Tutu;
- особенности Tutu могут проникать в последующую логику;
- при появлении другого провайдера общей модели пока не будет.

### 2. Tutu DTO + отдельная provider-independent domain model

Ответ Tutu сначала валидируется в типы источника, затем преобразуется в собственные `FlightOption`, `Fare`, `Money` и другие сущности продукта.

**Плюсы:**
- бизнес-логика меньше зависит от Tutu;
- удобнее объединять несколько провайдеров;
- внутреннюю модель можно оптимизировать под собственные алгоритмы.

**Минусы:**
- второй набор моделей и отдельный mapper;
- дополнительное место для потери `None`, цен, тарифных условий, пагинации и других фактов;
- нужно заранее определить понятия и границы domain model, которых текущие executable specifications ещё не требуют;
- повышает сложность первой реализации без подтверждённой пользы.

### 3. TypedDict

Отклонено. Он даёт статические подсказки, но runtime-данные остаются обычными словарями, доступ сохраняется через `["field"]`, а входной ответ MCP сам по себе не валидируется.

### 4. Генерация типов из MCP schema

Сейчас не подходит как основной путь. `tools/list` формально описывает вход `search_avia`, но богатая структура результата приходит как JSON внутри text content и не имеет достаточной output schema для генерации всей модели результата.

## Решение

Для первой реализации использовать **типизированную модель, повторяющую фактический ответ Tutu**, без отдельного provider-independent domain layer.

Граница данных:

```text
MCP / JSON
    ↓
parse + validation
    ↓
typed Tutu models
    ↓
product behavior
```

Сырые `dict` допустимы только на внешней интеграционной границе, где JSON физически входит в программу или передаётся наружу. После разбора ответа рабочий production-поток не должен передавать данные между этапами как произвольные словари.

Для runtime validation использовать Pydantic-модели. Модели должны отражать фактическую структуру Tutu и не вводить новые предметные абстракции без необходимости.

Денежное `amount` после разбора представляется точным числовым типом (`Decimal`), а не `float`. Даты и время разбираются в timezone-aware `datetime`, когда соответствующее поле присутствует в ответе.

Текущие словари в executable specification остаются языком наблюдений теста и не являются внутренней архитектурой production-кода. При необходимости `tests/product_driver.py` может адаптировать типизированный результат продукта к форме наблюдений теста.

## Почему принято это решение

Текущая задача — корректно реализовать один источник по уже записанному фактическому контракту. Отдельная domain model пока не решает подтверждённую проблему, но создаёт дополнительное преобразование и новые архитектурные решения.

Типизированная модель источника уже устраняет главную проблему — неструктурированный поток `dict` — при минимальном объёме новой архитектуры.

Это соответствует принятому порядку разработки: сначала наблюдаемое требование и исполняемая спецификация, затем минимальная реализация, а новые слои появляются только при фактической необходимости.

## Когда решение пересмотреть

Отдельная provider-independent модель становится обоснованной, если executable specification потребует хотя бы одно из следующего:

- объединять результаты Tutu с другим провайдером;
- применять общее поведение к данным разных форматов;
- существующая структура Tutu объективно мешает реализации нужного алгоритма;
- повторяющиеся преобразования показывают устойчивую собственную предметную модель.

До появления такого требования дополнительный domain layer не вводится.
